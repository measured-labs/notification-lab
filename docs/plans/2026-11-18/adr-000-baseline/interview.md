# 인터뷰 기록 — notification-lab ADR-000 기준선 (2026-11-18)

> 명세(requirement-spec.md)는 구현 차례(02 · 04 뒤)에 이 기록을 옮겨 합의받는다. 그때까지 이 폴더에는 이 파일만 둔다.

## 질문 · 답

1. 발송 구조 = **평범: 요청 안에서 동기 발송**(권장) — 알림 API가 트랜잭션 안에서 기록 저장 → 흉내 발송사 호출 → 결과 기록. 큐 · 우선순위 · 속도 제한 · 멱등키 없음. README의 Outbox → 우선순위 큐 → 토큰 버킷 → DLQ는 해법이라 기준선에 넣지 않는다.
2. 재시도 = **즉시 고정 3회**(권장) — README 근거 '지수 백오프 없는 재시도가 부하를 증폭'을 관측하기 위해.
3. 기능 = 트랜잭셔널 알림 API · 캠페인 발송 API · 발송 이력 조회 · **채널 여럿(push · SMS · email)**.
4. 흉내 발송사 = **최소 · 별도 모듈**(권장) — 분당 쿼터(정각과 어긋난 창) · 429 · 5xx · 지연 · 응답 유실 무작위 주입. 발송 기록 덤프 · 중복 집계 API 없음(판정기 ADR에서 필요가 드러나면).
5. 채널 구성 = 사용자: "1번으로 하되 2번으로 추후 확장해야되겠네 대용량 트래픽으로 가면" → **모듈 하나 · 채널별 경로 · 쿼터 · 장애 설정**, 대용량에서 채널별 분리는 그 ADR에서.
6. 캠페인 발송 = 사용자: "보통이런건 2번으로 처리할 꺼라 생각하는데 어떻게 생각해?" → 동의(메인 근거: 실무 첫 코드는 스레드 풀 병렬 · 단일 스레드는 초당 수십 건이라 쿼터 · 429 · 재시도 증폭 · 트랜잭셔널과의 경쟁을 가린다 — 기준선 원칙 '문제를 가리지 않을 것' 위반) → **채널별 행 · 캠페인은 스레드 풀 병렬(크기 설정 · 속도 제한 없음)**.
7. stakes = **중간** · 기반 = 02와 같게(PostgreSQL 16 + JPA + Flyway · repo docs · feat/adr-000-baseline · auto · 명세는 구현 차례에).
